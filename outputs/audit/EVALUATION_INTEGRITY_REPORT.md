## 1. Audit Inquiries & Findings

### Q1: Was the ground-truth root cause accidentally included in the model prompt?
- **Pre-Audit State**: `data/evaluation_cases.json` combined telemetry and answer keys in a single JSON schema.
- **Remediation**: Completely separated into `data/evaluation_cases.json` (model inputs) and `data/evaluation_ground_truth.json` (evaluator labels). Implemented `_sanitize_telemetry()` in `core/llm_engine.py` to scrub any ground-truth fields before prompt construction.
- **Verification**: Audited prompt generation; confirmed zero ground-truth tokens in prompt strings.

### Q2: Was the expected resolution passed directly to the LLM?
- **Finding**: No expected resolution was passed to the LLM. In Memory ON, only past verified postmortems stored in Hindsight were retrieved via semantic search.

### Q3: Were evaluation outputs generated by hardcoded mappings?
- **Finding**: In offline preview mode, deterministic expert logic was used. To ensure generalizability, 6 new holdout test cases were added (total 12 cases), including conflicting evidence and different underlying causes.

### Q4: Was Hindsight retrieval genuine?
- **Finding**: In live mode, `client.recall()` calls the Hindsight API on bank `opsrecall-demo`. In offline mode, the system clearly marks memories as `OFFLINE_PREVIEW` and never claims a mock is live Hindsight.

### Q5: Did Memory OFF receive any hidden historical context?
- **Finding**: Verified that Memory OFF runs with `recalled_memories = []` and prompt section explicitly stating: `=== HISTORICAL MEMORY DISABLED ===`. Zero historical context is passed to the baseline model.

### Q6: Was the scoring formula transparent and defensible?
- **Remediation**: Decomposed the composite score into 7 independently reported metrics (Root cause top 3, relevant retrieval, failed fix avoidance, false recall resistance, grounding, uncertainty handling, distractor rejection). Documented exact point weights (30/20/20/15/5/5/5).
